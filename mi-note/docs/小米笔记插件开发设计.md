# 小米笔记插件开发设计

本文描述待实现的一套完整工作流。主要用途是在 Windows 上整理工作规范，保存为 Markdown，再同步到小米笔记供手机查阅。使用一个小米账号。每个笔记工作区对应一个独立的 Windows 文件夹，DSH 会话的工作目录与插件同步目录指向同一个位置。

本文件是交给 DSH 创造模式从头开发的完整规格。交付物是一个可安装的 bundle，包含 Host 登录与同步服务、插件设置与左侧快捷入口，以及可选的「小米笔记」Agent 预设。先用 `cordis_inspect_list`、`cordis_inspect_query` 核对运行版本的服务、配置、导航插槽和预设接口，再用 `plugin_manager install_bundle` 安装。以真实界面和新建预设会话验收注册结果。 [DSH 官方工具目录](https://deepseek-harness.github.io/deepseek-harness/en/reference/tool-catalog) · [DSH 持久化插件流程](https://deepseek-harness.github.io/deepseek-harness/en/develop/practice/dynamic-cordis)

## 工作区、界面与 Agent

| 位置 | 职责 |
|---|---|
| Windows 笔记工作区 | 保存可直接编辑的 `.md` 文件。用户用 Windows 编辑器，Agent 用 DSH 的工作区文件能力，双方编辑同一份文件。 |
| DSH 原生界面 | 使用现有文件树、右侧预览、文件刷新和 Windows 软件打开能力。撤下插件自建的右侧入口、文件浏览器和 Markdown 渲染器。左侧提供「小米笔记设置」快捷入口，复用同一设置页。 |
| 小米笔记插件 | 设置页负责账号连接与工作区配置。Host 负责现有扫码登录和续期、笔记与文件映射、双向同步、格式兼容检查和冲突保护。 |
| 「小米笔记」Agent 预设 | 以规范整理和写作为主，也可以搜索、整理文件及协助合并。默认通过本地文件和同步工具完成操作，读写范围由用户在 DSH 会话中指定。 |

左侧入口按部署版本支持的 DSH 导航接口接入，实现前核对设置页能否直接定位到插件。工作区路径显式配置为绝对路径，换会话时沿用同一个目录。配置页显示实际同步目录。插件保留设置和同步接口，日常编辑、预览、刷新与打开文件由 DSH 或 Windows 承接。

## 扫码登录与纯 HTTP 续期

设置页显示「连接小米账号」「已连接」「重新连接」和「断开」等与当前状态相符的操作。页面打开时从 Host 读取本地账号状态。用户点击连接，看到二维码、有效期和取消入口，在手机上扫码确认。校验并保存成功后显示已连接，由用户发起拉取。Host 使用 Node HTTP 完成授权与换票，DSH 客户端只显示二维码和状态。整套流程无需启动 Chrome、启用 CDP 或读取浏览器 Cookie。

### 首次登录

1. Host 请求 `GET https://i.mi.com/api/user/login?followUp=https%3A%2F%2Fi.mi.com%2F&_locale=zh_CN`。取 `data.loginUrl`，检查目标为预期的账号服务地址，使用完整 URL 并追加 `_json=true`。解析账号服务 JSON 前去掉 `&&&START&&&` 前缀，读取 `sid`、`qs`、`callback`、`_sign` 和 `serviceParam` 等扫码参数。
2. 使用这些参数请求 `account.xiaomi.com/longPolling/loginUrl`。为本次登录生成设备标识并在后续请求中沿用。服务器返回用于二维码的 `loginUrl`、用于 Host 长轮询的 `lp` 及有效期。实测地址形态为 `ak.account.xiaomi.com/longPolling/login` 和 `ak.lp.account.xiaomi.com/lp/s`。按不同用途校验小米 HTTPS 主机和路径，支持经核实的地区域名形态。二维码在本地渲染，Host 保留长轮询地址和其余授权参数。 [上游扫码实现](https://github.com/Guyuepp/xiaomi-drive-go/blob/main/login.go#L201)
3. Host 在挑战有效期内等待小米长轮询结果。确认成功要求 HTTP 成功、`code=0`、`securityStatus=0`，并返回有效的 `location`、`passToken` 与 `userId`。业务失败也可能有 `location`，只有成功响应才进入换票。取消、过期或额外验证要求都返回明确状态。设置页只在扫码期间查询 Host 状态，关闭页面后停止前端查询。
4. Host 请求 `location` 指向的 `i.mi.com` 换票地址，手动跟随最多六次 HTTP 请求，逐跳读取独立的 `Set-Cookie`，取得非空 `serviceToken`。每一跳校验预期 HTTPS 主机与用途，按目标分配 Cookie。用新 `serviceToken` 和 `userId` 请求笔记列表，`limit=1` 且业务返回成功后才保存。 [上游换票实现](https://github.com/Guyuepp/xiaomi-drive-go/blob/main/login.go#L87)
5. 将已验证的 `serviceToken`、`passToken`、`userId` 和登录所用 `deviceId` 保存到当前 DSH profile 的凭据库。使用插件专用凭据引用，持久化读取需要识别凭据库来源。未通过校验或未保存成功的候选会话保留原登录态。断开时删除已保存凭据并撤销在途任务，重启后维持断开。

### 会话状态与凭据边界

- 同一个插件实例同时只创建一个扫码挑战。并发发起操作应共用创建中的任务。Host 为挑战生成随机会话标识，状态包括等待确认、验证中、已连接、已过期、已取消和失败。取消后即使旧轮询迟到，也无法提交凭据。新挑战、断开和插件卸载应取消相关任务。有效期以小米响应为准。
- 复用 DSH 当前版本提供的 Client → Host 通道和认证能力。开始扫码、取消、断开、保存配置等写操作校验调用身份与来源，使用 HTTP 时用 `POST`。确认当前通道确实有 Host 侧认证，不能仅靠自定义请求头推断。扫码与断开属于设置页的用户操作。前端只收到二维码、状态和必要的打码信息。完整换票 URL、长轮询地址、原始响应和令牌留在 Host。
- 凭据提交串行化。保存前在提交边界核对挑战、账号和版本，防止已经取消的扫码、旧续期或旧账号结果覆盖当前凭据。网络错误和业务错误输出稳定的分类与安全提示。日志、前端响应和 Agent 输出省略令牌、原始账号响应和签名 URL。

### 云端请求按需续期

1. 明确收到笔记接口 `401` 后，先核对失败请求使用的账号和当前凭据版本。同一账号已有更新时可重试；账号已经切换或断开时终止旧请求。仍需续期的同一账号和凭据版本共用一次换票，单个调用取消只结束自己的等待。
2. 重新从 `i.mi.com/api/user/login` 获取服务端提供的完整 `loginUrl`，带 `passToken`、`userId` 和扫码时的 `deviceId` 恢复账号会话。实测请求还带了 `pass_ua=web`。检查成功状态后复用 `/sts` 换票和笔记只读校验。确认账号与凭据版本未变，再提交新凭据。 [上游续期实现](https://github.com/Guyuepp/xiaomi-drive-go/blob/main/session.go#L432)
3. 重试边界是被 `401` 拒绝的单次 HTTP 请求，每次最多重试一次。若写接口同时要求 Cookie 与表单中的 `serviceToken`，两处都用新值。网络中断、超时等结果不明的写请求交给调用方核对结果，避免重复执行整批操作或重复创建笔记。
4. 长期凭据缺失、被账号服务明确拒绝或要求再次交互时，提示重新扫码。临时网络错误、限流、`5xx` 和只读校验的临时失败保留原凭据，允许以后重试。换票后明确无法访问云笔记时说明是访问校验失败。普通笔记接口只携带服务所需的短期凭据。

### 已验证的协议与集成验收

2026-11-13 用 Node.js `v24.19.0` 和真实小米账号执行了独立协议测试。旧 `serviceToken` 请求笔记返回 `401`，旧长期凭据恢复返回 `70016`，附原设备字段结果相同。新二维码有效期为 300 秒，手机确认后返回 `code=0`、`securityStatus=0`。首次 `/sts` 第一跳返回 `302` 并下发令牌，笔记只读校验成功。随即用新会话的长期凭据纯 HTTP 恢复，再次得到不同的 `serviceToken`，第二次笔记只读校验成功。测试令牌只在内存中使用。

上述证据覆盖扫码授权和立即换票。新 bundle 仍需实际验证设置页扫码、取消和过期状态、凭据持久化与 DSH 重启、短期令牌失效后收到 `401` 的自动恢复、并发续期、断开和账号状态更新。用模拟响应覆盖 `70016`、`503`、异常重定向、旧任务迟到及重试一次的行为。

## 日常指令与云端操作

| 用户指令 | 预期行为 |
|---|---|
| 「整理这篇规范」 | Agent 编辑指定的本地 Markdown 并报告变动。 |
| 「整理这篇规范并同步」 | Agent 编辑后检查选中文件，能安全提交时直接推送，并报告结果。 |
| 「同步这篇」 | 将当前指定文件推到它关联的小米笔记。云端也有改动时返回冲突。 |
| 「发布这篇」 | 将用户指定、尚未关联的本地文件创建为云笔记，并记录返回的笔记 ID。 |
| 「拉取这篇」或「拉取云端」 | 将指定笔记或云端列表更新到本地，保护已经编辑的文件。 |
| 「合并这篇」 | 提供本地、云端和上次同步的正文供 Agent 比较，生成合并稿。「合并并同步」在合并无歧义且检查通过时可以提交。 |

Windows 编辑器保存、文件移动和 DSH 文件刷新都只改变本地状态。用户指令决定实际推送范围，未指定且上下文无法确定目标时由 Agent 询问。多个文件可一次提交，某篇存在冲突时继续处理其他可安全提交的文件，并逐篇报告成功、未变、冲突或失败。删除本地文件只标记本地副本缺失。移入云端回收站沿用独立的云端操作与明确指令。

## 笔记身份、路径与同步基线

插件维护 `.mi-note-map.json` 及插件管理的基线正文。每条记录至少包含云笔记 ID、上次同步路径、云端 `tag`、云端标题和目录标识、上次提交或拉取时的本地哈希，以及用于三方比较的正文。发生转换归一化时分别保存上次提交的本地版本与云端读回的基线，避免同一处格式差异被反复识别为新编辑。基线资料属于插件内部文件，排除在发布范围外。

**文件名与目录参与同步。** 建议以 `.md` 文件名作为推送重命名时的云端标题，以工作区内的目录映射云端分类。初次拉取时保留原云端标题、目录 ID 与生成路径的对应关系。Windows 文件名清洗、重名后缀与大小写规则由插件处理。原路径未改变时，保留已有的云端标题和分类。目录改名或移动后的整批结果先列出，按用户指定范围应用。云端目录缺失、重名或层级不兼容时返回具体问题，避免把笔记写入错误分类。目录创建、移动能力以本项目接口实测为准。

**重命名和移动必须沿用原云笔记 ID。** 普通 Markdown 保持可直接编辑。插件先用已有路径找关联。原路径消失且出现唯一的相同内容文件时，用同步基线识别候选移动。若同时移动并改正文、出现相同内容的多份文件，或其他证据无法唯一确定，则列出候选，由用户或 Agent 指定原笔记与新路径的绑定。绑定确认前，推送不能把疑似移动的文件自动当成新笔记。云端标题、目录和 `tag` 校验成功后再提交路径变更。

已有映射要兼容读取。缺少三方基线时，可以先依赖原哈希和 `tag` 判断冲突，并在下一次安全拉取或提交时补齐正文。列表未取全、分页失败或映射读取失败时，保留已有记录并报告原因。同步内部文件写入采用原子替换，同一工作区的同步写操作串行。调用真实云端写入前复核选中文件内容，写入后若文件又被外部编辑器保存，只记录刚提交的版本，保留新编辑为待同步。

## 拉取、预检与推送

1. `status` 读取本地文件和映射，列出未改、本地已改、新文件、可能移动和本地缺失。仍可沿用已有 `pull`。拉取同时检查 `tag` 与本地哈希，只有云端变化且本地未改时可更新文件和基线。两边都改时保留本地和云端内容供比较。云端笔记缺失时保留本地稿及可追踪的关联状态。
2. 推送预检读取选中文件、映射和最新云端状态，返回每篇计划变更、格式问题、标题或分类变更、冲突及需要补充的绑定信息。文件选择使用工作区内相对路径，限制在配置目录内，拒绝通过绝对路径、越界相对路径或链接访问工作区外的文件。
3. 推送复用已有的笔记创建和更新请求。提交时重新核对笔记 ID、文件哈希与云端 `tag`，使用云端乐观锁。只改标题或分类时保留正文和附件字段。发布时才创建笔记。若创建请求结果不确定，先核对云端结果再决定是否重试，以免创建重复笔记。
4. 成功后记录云端返回或重新读取的版本，更新路径和同步基线。保留用户保存的本地 Markdown。云端转换结果可单独查看。遇到冲突时由 Agent 展示差异和合并建议，明确确定合并目标后再按最新 `tag` 提交。

小米笔记接口的已用路径均相对于 `https://i.mi.com`。列表和登录校验使用 `GET /note/full/page/`，详情使用 `GET /note/note/{id}/`，新建和更新分别使用 `POST /note/note` 与 `POST /note/note/{id}`。云端目录的创建和更新分别使用 `POST /note/folder` 与 `POST /note/folder/{id}`。写操作表单带 `serviceToken`。更新时读取完整云端记录，保留服务返回的附件等字段，并提交 `tag` 让云端检测冲突。接口属于小米网页服务，响应结构与可写字段由新实现通过只读观察、样例和测试笔记核对。 [小米笔记 CLI 的公开实现](https://github.com/ceynri/mi-note-cli)

### 已摸清的读写契约

旧插件的云端客户端与公开 `mi-note-cli` 都提供笔记读取、创建、正文更新、移动和目录管理。旧 DSH 插件的工作区同步只实现了 `status` 和 `pull`。新实现可以从这些接口和公开的三方同步实现着手，工作区的路径识别、显式发布、冲突和失败恢复按本文规则实现。 [公开 CLI 的同步与数据安全说明](https://github.com/ceynri/mi-note-cli#导出-vs-同步)

| 操作 | 请求及处理规则 |
|---|---|
| 读列表 | `GET /note/full/page/?ts=…&limit=…`，后续页传 `syncTag`。成功结果的 `data.entries` 为笔记，`data.folders` 为目录，按 ID 汇总。`data.lastPage` 表示完成。上限截断、游标缺失或停滞、请求失败均报告列表不完整。`syncTag` 是列表游标，单条笔记的 `tag` 用于写入版本检查。 |
| 读详情 | `GET /note/note/{id}/?ts=…`，以 `result=ok` 且有 `data.entry` 为成功。拉取正文时以完整详情为准，列表里的 `snippet` 只用于摘要和选取目标。 |
| 新建笔记 | `POST /note/note`，`application/x-www-form-urlencoded` 表单包含序列化的 `entry` 和 `serviceToken`。`entry` 包含 XML `content`、派生的 `snippet`、标题 `extraInfo.title`、`folderId`、时间和普通笔记所需的默认字段。以服务端返回的笔记 ID 关联本地文件。 |
| 编辑或移动 | `POST /note/note/{id}`，表单仍为 `entry` 和 `serviceToken`。由最新完整条目组装，带读到的 `id`、`tag`，仅应用用户指定的字段变更。改标题更新 `extraInfo.title`，移动更新 `folderId`。只改标题或分类时沿用原 XML。正文修改先转 XML，再更新摘要。保留经验证可写的原有元数据与附件关联。 |
| 目录与回收站 | 创建目录使用 `POST /note/folder`，更新目录使用 `POST /note/folder/{id}`，载荷包括 `type=folder`、名称 `subject` 及父级 `folderId`。根目录约定为 `0`。显式移入回收站用 `POST /note/full/{id}/delete`，表单包括 `tag`、`purge=false` 和 `serviceToken`。本地删除只影响本地。 |

写操作同时检查 HTTP 状态和业务 `result`。旧客户端识别 `data.conflict` 为版本冲突。更新成功响应可能省略 `data.entry`，应再读详情获取服务器实际保存的正文和新 `tag`。旧实现会回退到请求中的条目，不能把它当作新的云端版本写入映射。云端明确拒绝时保留当前基线。超时、连接中断或提交后详情读取失败时，记录为结果待核对，通过笔记 ID 读回确认。新建结果不明且缺少 ID 时，报告候选和不确定性，避免盲目重复创建。

### 双向同步的判定与恢复

| 本地状态 | 云端状态 | 处理 |
|---|---|---|
| 已关联，文件和路径都未变 | 版本未变 | 返回未变。 |
| 本地未改 | 云端版本变化 | 拉取详情并更新本地和基线。云端标题或目录变化时，先检查目的路径，安全时移动同一份本地副本。 |
| 正文或路径变化 | 云端版本未变 | 用户指定同步后推送。路径变化按原 ID 提交改名或移动。 |
| 正文或路径变化 | 云端也变化 | 记录冲突，保留本地、云端与基线。若当前内容及元数据已一致，只更新基线。 |
| 本地文件缺失 | 云端仍存在 | 保留关联，标记本地缺失或待确认移动。可以明确指定恢复本地副本。 |
| 未关联 | 无明确对应笔记 | 保留为本地草稿。只有显式发布才创建。首次拉取碰到同名不同内容时保留两边。 |
| 任意 | 云端缺失或状态未核实 | 保留文件和关联。分页不完整时标记未核实。云端确实删除后，用户可以保留本地副本或明确重新发布。 |

预检结果应绑定所选路径、文件哈希、云端 ID 与版本。执行时重查，计划过期的文件单独跳过。分批读取云端结果时按 ID 更新已有映射。旧版离线复现显示，按云端新标题重新落盘会留下旧文件，且截断列表会丢掉未返回笔记的映射。新实现应复用既有 ID 与路径记录，安全更新后再提交映射，并覆盖这两个回归场景。云端写入与本地落盘之间无法共用事务，已确认的云端写入应可在下次操作时通过详情恢复记录。

### 验证记录与仍需实测的范围

- **本次离线核对。** 用模拟 HTTP 响应运行旧客户端，确认列表和详情的 `GET` 路径、新建和更新的 `POST` 路径，以及 `entry` 和 `serviceToken` 两个表单字段。用规范样稿验证 Markdown → XML → Markdown 保留 `30 mm` 和例外条款。只改标题和目录的载荷保留原 XML 与 `tag`。临时目录复现了旧拉取的改名和截断缺陷。
- **本次格式样例。** H1/H3 样例可以往返。表格和带语言的代码围栏样例往返发生变化。旧转换入口拒绝本地图片及与正文同行的图片，独占行的 `minote://image/{fileId}` 可生成小米图片标签。图片完整回读、表格可读性及附件保真仍需以实际载荷和手机显示验证。 [公开 CLI 的附件规则](https://github.com/ceynri/mi-note-cli#在笔记中插入图片)
- **新 bundle 的真实账号验收。** 用单独的测试目录和测试笔记依次确认首次拉取读到完整正文，Windows 修改后更新同一 ID，改文件名和移动后手机端显示正确标题及目录，手机先改后能发现 `tag` 冲突，重新拉取不会覆盖本地未同步编辑。另验证目录可用层级、附图笔记编辑后的图片保留、同名处理，以及新建结果不明确时的核对流程。核对完按测试范围清理。当前记录来自源码、模拟响应与公开实现，本次没有对真实账号发起笔记写入。

## 格式兼容与规范写作

DSH 预览用于检查 Markdown 阅读效果。小米兼容性由 Host 按实际转换能力校验，预检与最终推送共用同一套规则。以转换器往返测试和手机回读验证确定支持清单。若参考或复用公开转换代码，保留其来源和相应的许可证说明。 [小米笔记 CLI 的转换参考](https://github.com/ceynri/mi-note-cli)

- **已有转换能力。** 普通段落、H1–H3、嵌套列表、复选框、引用、分割线、常见行内格式和链接可以作为规范正文的基础，具体组合通过转换往返测试确认。
- **可能降级的内容。** 对表格、脚注、定义列表、H4 以上标题、代码围栏及语言标识、内嵌 HTML、本地图片和附件逐项验证。预检指出文件、位置和可预见的损失。无法保留条款、数字、单位或附件引用时阻止提交。轻微排版变化可提示后按配置的兼容规则处理。
- **工作规范写作。** 预设优先使用短标题、条款号、有序列表和清晰的单位。Agent 转写表格时可以改用分组列表，保留项目名称、阈值、适用条件及例外。附件和复杂表格的使用需求尚待实际样稿确认，以预检结果决定能否发布。

## Agent 预设与验收

提供可选的「小米笔记」DSH Agent 预设，沿用 DSH 的工作区文件权限与用户指令范围。预设引导 Agent 先改本地文件，推送通过 `mi_note_sync` 的预检和提交入口，避免日常编辑绕开映射直接调用云端增删改。常规会话可关闭插件的全局工作流提示。预设可按部署版本使用 DSH bundle 声明工具、提示词及技能。

| 场景 | 验收结果 |
|---|---|
| Windows 手动编辑与 DSH Agent 编辑 | 两者打开同一物理文件，保存后 DSH 原生预览能看到变化。右侧仅使用 DSH 原生工作区能力，左侧入口能到达插件设置。 |
| 拉取、推送和发布 | `pull` 能建立映射，推送只处理用户指定的已关联文件，显式发布才创建新笔记。成功后在手机查看规范正文，并核对条款、数字和单位。 |
| Windows 重命名与移动 | 对唯一可识别的移动沿用原笔记 ID，同步标题与分类。模糊移动返回候选；本地删除不会触发云端删除。 |
| 冲突、格式与批量 | 手机端和本地都修改时保留双方及基线，显示冲突。格式丢失可定位，单篇失败不影响其他可提交文件。 |
| 兼容与恢复 | 旧映射可加载，部分拉取与请求失败后映射仍可继续使用。新设置页可扫码并保存登录态，实际 `401` 后可自动换票并重试。 |

用临时目录和模拟云端验证映射、格式、重命名、冲突和并发。用测试笔记验收 DSH 原生预览、Windows 保存、Agent 预设、手机阅读及真实标题和目录更新。交付报告注明 bundle 路径、DSH 安装及激活结果、自动化用例结果，以及真实账号和手机端的验收结果。把独立协议实测、模拟测试和新 bundle 实机结果分别记录。

### 预设提示词

```text
你是「小米笔记」工作区的写作助手。你的主要任务是把工作规范、标准、操作规程和检查清单整理成适合手机阅读的 Markdown。以当前 DSH 会话的笔记工作区为文件范围。优先使用用户打开或指定的文件，按用户要求搜索或整理多个文件。用户和你编辑的是同一份本地文件，保存后可以用 DSH 原生预览查看。

写作时优先使用短标题、条款号、有序列表和分组列表。保留原规范的条款、数值、单位、适用条件、例外和来源。区分原文要求与整理建议。遇到依据不足的数值、标准版本或要求，保留不确定性并指出需要核对的地方。把表格改成列表时，逐项保留字段含义和对应关系。

按用户指令执行：

- 「整理这篇」「编辑这篇」：修改本地 Markdown，汇报保存位置和主要改动。
- 「整理并同步」：先保存本地修改，再预检指定文件。可安全提交时直接推送，不再要求重复确认。
- 「同步这篇」：预检并推送指定的已关联文件。发现云端有改动时报告冲突。没有关联的文件提示用户用「发布」明确创建。
- 「发布这篇」：预检用户指定的新文件，通过后调用插件创建云笔记。可能是已关联文件移动后的新路径时，先确定原笔记身份。
- 「拉取这篇」「拉取云端」：调用插件拉取指定笔记或云端列表，保留已有本地编辑。
- 「合并这篇」：比较本地、云端和上次同步的正文，说明差异并生成合并稿。「合并并同步」时，只有合并结果明确且预检通过，才提交到云端。

编辑和同步以用户指定的文件为准。上下文能唯一识别目标时直接处理。存在多个候选时，列出相对路径并请用户选定。工作区内重命名或移动后，使用插件识别并保留原云笔记 ID，由同步更新云端标题和分类。匹配不唯一时展示候选，确定对应关系后再提交。本地删除只移除本地副本，云端移入回收站需要单独的明确指令。

所有云端读写通过插件工具。用预检结果判断格式兼容性，说明受影响的位置以及会丢失的内容。若条款、数字、单位或附件引用会丢失，先提出保真的改写方案。遇到冲突保留本地和云端版本，使用插件提供的基线比较。批量操作继续处理可安全提交的文件，逐篇报告成功、未变、冲突或失败。写入结果不明确时先核对云端结果，避免重复发布。需要登录时，引导用户打开「小米笔记设置」扫码或重新连接。

完成后报告实际变更和同步结果。编辑只在本地完成时给出文件路径。云端同步成功时列出已提交的文件。冲突、格式损失和其他未完成项各说明具体原因与下一步。
```
